# Тестовое приложение ESP32 Platform BLE

## Назначение

В корне репозитория находится ESP-IDF приложение для проверки инициализации NimBLE, получения BLE advertising reports, generic driver registry и доставки driver events. Оно использует встроенный тестовый драйвер и не подключает драйверы конкретных устройств.

## Требования

- ESP-IDF 6.1;
- плата на ESP32-C3;
- BLE-устройства или телефон с включённым Bluetooth advertising поблизости.

## Сборка

Из корня репозитория:

~~~bash
idf.py set-target esp32c3
idf.py build
~~~

## Прошивка и монитор

~~~bash
idf.py -p PORT flash monitor
~~~

В логе ожидаются сообщения о запуске NimBLE host, синхронизации и запуске сканирования, после чего должны появляться строки ADV с BLE-адресом, RSSI и длиной advertising payload.

## Что проверяет этот тест

1. Инициализацию NVS приложением до запуска BLE.
2. Инициализацию NimBLE через platform_ble_init().
3. Синхронизацию NimBLE host.
4. Запуск passive scan.
5. Преобразование GAP advertising report в platform_ble_adv_packet_t.
6. Регистрацию тестового BLE-драйвера до запуска scan.
7. Вызов matches() и on_advertisement() для рекламных пакетов с непустым payload.
8. Доставку тестового события приложению через platform_ble_device_emit_event().

## Владение NVS

ESP-IDF NimBLE использует NVS на этапе инициализации контроллера. Поэтому приложение должно вызвать nvs_flash_init() до platform_ble_init(). BLE Core намеренно не инициализирует и не стирает NVS: хранилище является общим ресурсом приложения, и автоматическое стирание могло бы удалить чужие настройки.

Если nvs_flash_init() возвращает ошибку из-за несовместимой или повреждённой NVS-разметки, решение о восстановлении принимает приложение.

## Проверка Driver Registry

Тестовое приложение регистрирует драйвер `ble_test_driver`. Он принимает рекламные пакеты с непустым payload и увеличивает счётчик обработанных пакетов. Каждые 100 пакетов драйвер отправляет событие с идентификатором `1`; приложение выводит строку вида:

~~~text
Driver event from ble_test_driver: processed 100 advertising reports
~~~

Счётчик нужен только для проверки маршрута `scan → registry → driver → event callback`. Он не является частью публичной модели BLE и не задаёт формат событий для реальных драйверов.

## Замечание о логировании

Тестовое приложение выводит подробную информацию о каждом advertising report, чтобы упростить первоначальную отладку. При большом количестве устройств такой вывод может создавать заметную дополнительную нагрузку и замедлять обработку. Это особенность диагностического приложения, а не обязательное поведение BLE Core.

Для нагрузочных проверок следует отключить логирование каждого пакета или ограничить его частоту (например, выводить агрегированную статистику раз в заданное число пакетов). В реальных драйверах не следует логировать каждый принятый advertising report без необходимости.

## Ограничения текущего этапа

- Тестовый driver registry проверяет базовую регистрацию, dispatch и доставку событий; отдельные unit-тесты граничных случаев registry ещё не добавлены.
- GATT client, соединения, bonding и notifications пока не реализованы.
- Аппаратная проверка на ESP32-C3 подтвердила синхронизацию NimBLE host, запуск passive scan, получение advertising reports, обработку пакетов через `ble_test_driver` и доставку application event с количеством обработанных пакетов (после каждых 100 reports).
- До сборки и проверки на реальной плате реализация считается предварительной.
