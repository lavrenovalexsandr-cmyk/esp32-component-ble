# Тестовое приложение ESP32 Platform BLE

## Назначение

В корне репозитория находится ESP-IDF приложение для проверки инициализации NimBLE, получения BLE advertising reports, generic driver registry и доставки driver events. Оно использует встроенный тестовый драйвер и не подключает драйверы конкретных устройств.

## Требования

- ESP-IDF 6.1;
- плата на ESP32-C3;
- BLE-устройства или телефон с включённым Bluetooth advertising поблизости.

## Сборка

Из корня репозитория:

~~~bash
idf.py set-target esp32c3
idf.py build
~~~

## Прошивка и монитор

~~~bash
idf.py -p PORT flash monitor
~~~

В логе ожидаются сообщения о запуске NimBLE host, синхронизации и запуске сканирования, после чего должны появляться строки ADV с BLE-адресом, RSSI и длиной advertising payload.

## Что проверяет этот тест

1. Инициализацию NVS приложением до запуска BLE.
2. Инициализацию NimBLE через platform_ble_init().
3. Синхронизацию NimBLE host.
4. Запуск passive scan.
5. Преобразование GAP advertising report в platform_ble_adv_packet_t.
6. Регистрацию тестового BLE-драйвера до запуска scan.
7. Вызов matches() и on_advertisement() для рекламных пакетов с непустым payload.
8. Доставку тестового события приложению через platform_ble_device_emit_event().

## Владение NVS

ESP-IDF NimBLE использует NVS на этапе инициализации контроллера. Поэтому приложение должно вызвать nvs_flash_init() до platform_ble_init(). BLE Core намеренно не инициализирует и не стирает NVS: хранилище является общим ресурсом приложения, и автоматическое стирание могло бы удалить чужие настройки.

Если nvs_flash_init() возвращает ошибку из-за несовместимой или повреждённой NVS-разметки, решение о восстановлении принимает приложение.

## Проверка Driver Registry

Тестовое приложение регистрирует драйвер `ble_test_driver`. Он принимает рекламные пакеты с непустым payload и увеличивает счётчик обработанных пакетов. Каждые 100 пакетов драйвер отправляет событие с идентификатором `1`; приложение выводит строку вида:

~~~text
Driver event from ble_test_driver: processed 100 advertising reports
~~~

Счётчик нужен только для проверки маршрута `scan → registry → driver → event callback`. Он не является частью публичной модели BLE и не задаёт формат событий для реальных драйверов.

## Замечание о логировании

Тестовое приложение выводит подробную информацию о каждом advertising report, чтобы упростить первоначальную отладку. При большом количестве устройств такой вывод может создавать заметную дополнительную нагрузку и замедлять обработку. Это особенность диагностического приложения, а не обязательное поведение BLE Core.

Для нагрузочных проверок следует отключить логирование каждого пакета или ограничить его частоту (например, выводить агрегированную статистику раз в заданное число пакетов). В реальных драйверах не следует логировать каждый принятый advertising report без необходимости.

## Дополнительные проверки scan lifecycle и driver dispatch

Тестовое приложение дополнено сценарием: старт passive scan с duration 10 секунд, явная остановка через 2 секунды, пауза для завершения GAP procedure, повторный запуск active scan на 3 секунды и проверка автоматического завершения. Также зарегистрированы два последовательных тестовых драйвера: первый один раз возвращает ESP_FAIL, второй должен продолжать получать пакеты. Счётчики проверяются в конце сценария. Проверки собраны и выполнены на ESP32-C3. В логе подтверждены ручная остановка passive scan, успешный повторный запуск active scan, автоматическое завершение active scan с reason=0 и состояние active=0 после завершения. Счётчики failing и following driver совпали: 145/145, что подтверждает продолжение dispatch после ESP_FAIL.

## Проверка duplicate filtering и Scan Response

В тестовом приложении реализован и проверен на ESP32-C3 следующий сценарий:

1. Passive scan на 6 секунд с `filter_duplicates=false`.
2. Подсчёт общего количества reports и повторов одинаковой сигнатуры: BLE address + address type + hash advertising payload.
3. Passive scan на 6 секунд с `filter_duplicates=true` и теми же счётчиками.
4. Active scan на 10 секунд с отдельным подсчётом reports, помеченных `scan_response=true`.

Фактический результат:

- `filter_duplicates=false`: 153 reports, 27 уникальных сигнатур, 126 повторов;
- `filter_duplicates=true`: 29 reports, 29 уникальных сигнатур, 0 повторов;
- active scan: 383 reports, 46 уникальных сигнатур, 337 повторов, 132 Scan Response.

Результат подтверждает работу duplicate filtering и получение Scan Response. Сравнение сигнатур является диагностикой тестового приложения: учитываются BLE address, address type, длина и hash payload. Меняющийся payload и ротация случайных адресов могут влиять на статистику в других радиоусловиях.

## Проверка BLE address и порядка байтов

В публичном API принято единое соглашение NimBLE: `platform_ble_addr_t.val[0]` — младший (правый) октет, `val[5]` — старший (левый). Для отображения адреса используется обратный порядок индексов `val[5]:...:val[0]`. Копирование из NimBLE GAP report и передача адреса в driver event не должны менять байты.

Startup self-test передаёт тестовый адрес `{0, 1, 2, 3, 4, 5}` через `platform_ble_device_emit_event()`, проверяет побайтовое совпадение в event callback и проверяет форматирование в `05:04:03:02:01:00`. После сборки и запуска ожидается сообщение `BLE address byte order test passed`. Это проверяет транспорт и форматирование тестового приложения; сопоставление с внешним BLE scanner выполняется отдельно на одном и том же устройстве.

## Результаты аппаратной проверки

На ESP32-C3 успешно выполнены startup self-tests Driver Registry: invalid descriptor, duplicate ID, лимит в 8 драйверов, отказ переполнения, unregister, повторный unregister, повторное использование слота, доставка event callback, отсутствие callback и неизвестный driver ID. В live scan подтверждено, что драйвер с matches() == false не получает on_advertisement(), при этом advertising reports продолжают поступать.

Ранее также подтверждены NimBLE host sync, passive scan, обработка пакетов через `ble_test_driver` и доставка application event после каждых 100 reports. В последнем сценарии подтверждены ручной stop и restart scan, active scan с конечной длительностью и изоляция ошибки драйвера: `ble_test_failing_driver` вернул ESP_FAIL, после чего `ble_test_after_error_driver` продолжил обработку; оба счётчика завершили тест со значением 145.

## Проверка повторной инициализации и deinit

После завершения основных scan-тестов приложение автоматически выполняет lifecycle-сценарий:

1. Останавливает первоначальный BLE экземпляр и проверяет, что initialized, host_synced и scan_active сброшены.
2. Повторно инициализирует BLE, ожидает NimBLE host sync, запускает continuous scan, проверяет поступление пакетов и останавливает scan вручную.
3. Выполняет deinit и проверяет сброс состояния.
4. Ещё раз инициализирует BLE, запускает finite scan на 3 секунды и проверяет автоматическое завершение.
5. Выполняет финальный deinit и проверяет сброс состояния.

Тест ожидает host sync не более 5 секунд после каждого init. Между этапами предусмотрены короткие паузы для завершения процедур NimBLE. Успешный сценарий заканчивается строкой:

~~~text
BLE init/deinit lifecycle tests passed
~~~

Аппаратная проверка на ESP32-C3 пройдена. В логе подтверждены остановка NimBLE host task, успешный deinit и завершение всего lifecycle-сценария.

Для сокращённого мониторинга lifecycle-теста можно использовать:

~~~bash
idf.py -p PORT monitor | grep --line-buffered -E "BLE lifecycle:|BLE init/deinit|NimBLE host task stopped|NimBLE stopped|assert failed|Guru Meditation|abort\\("
~~~

При deinit runtime-состояние scan сбрасывается, но callback сканирования и его context сохраняются. Поэтому при повторном init приложение может продолжать получать advertising reports без повторной регистрации callback. Driver registry и event callback также сохраняются.

## Ограничения текущего этапа

- Отдельные unit-тесты в тестовом framework пока не добавлены; проверки Registry реализованы как startup self-tests тестового приложения.
- Scan stop/restart, конечный duration, active scan и изоляция ошибки callback проверены на ESP32-C3.
- Duplicate filtering и фактическое получение Scan Response проверены на ESP32-C3: 153 reports / 126 повторов без фильтра, 29 reports / 0 повторов с фильтром; active scan получил 132 Scan Response.
- BLE address byte order, повторная инициализация и deinit проверены на ESP32-C3.
- GATT client, соединения, bonding и notifications пока не реализованы.
