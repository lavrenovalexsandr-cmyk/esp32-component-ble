# Проектирование публичного API ESP32 Platform BLE

## 1. Статус

Документ фиксирует предварительный публичный контракт первого этапа. Заголовки являются проектируемым API; реализация функций будет добавлена следующим этапом. До первой аппаратной проверки API может уточняться.

## 2. Общие правила

- Публичные функции возвращают esp_err_t там, где возможна ошибка выполнения.
- Конфигурации передаются через структуры.
- Callback выполняются в контексте NimBLE host task, если конкретная функция не документирует иное. Callback не должны блокироваться или выполнять длительные операции.
- Данные, передаваемые через указатели callback, принадлежат вызывающей стороне и не должны сохраняться без копирования.
- Core не владеет памятью пользовательского driver payload.
- Публичные заголовки не раскрывают типы NimBLE.

## 3. Lifecycle — platform_ble.h

Предполагаемые функции:

- platform_ble_init(config) — подготовка BLE подсистемы и NimBLE host;
- platform_ble_deinit() — остановка и освобождение ресурсов, если это допускается выбранной моделью ESP-IDF controller lifecycle.

Инициализация должна быть идемпотентной либо возвращать документированную ошибку повторного вызова. Точная модель владения controller/host будет проверена на используемой версии ESP-IDF до реализации.

## 4. Scan — platform_ble_scan.h

platform_ble_scan_start(config) запускает сканирование, platform_ble_scan_stop() останавливает его. Отдельный callback позволяет приложению наблюдать необработанные рекламные пакеты.

Scan config предусматривает active/passive scan, interval и window в единицах BLE 0.625 ms, duration в миллисекундах (0 означает без ограничения по времени), duplicate filtering.

Ограничения диапазонов и преобразование единиц проверяются в реализации.

## 5. Generic driver API — platform_ble_device.h

Descriptor драйвера содержит стабильный строковый id, callback matches для определения интереса к пакету, callback on_advertisement для протокольной обработки и пользовательский context.

Registry предоставляет регистрацию и снятие регистрации драйвера. Descriptor и context должны оставаться валидными до снятия регистрации.

Обработка пакета разделена на два этапа, чтобы дешёвое распознавание не вынуждало выполнять полный разбор каждого advertising report.

## 6. Driver events

platform_ble_device_event_t — транспортная оболочка, а не схема измерений. Она содержит driver_id, BLE address, event_id, определяемый драйвером, payload и payload_size.

Драйвер публикует событие через platform_ble_device_emit_event(). Приложение устанавливает общий callback приёма событий.

Payload может указывать на стековую или временную память драйвера и гарантированно валиден только на время callback. Если приложению нужно отложить обработку, оно копирует payload в собственную очередь/структуру.

## 7. Потоки выполнения

Первичная реализация предполагает, что NimBLE report callback вызывает scan callback и последовательный driver dispatch. Никакие длительные операции, сетевые публикации или блокирующие ожидания не должны выполняться внутри этого контекста. При необходимости приложение переносит обработку в собственную FreeRTOS queue/task.

Вопрос о выделенной очереди Core для driver events будет решён при реализации после оценки размеров payload, нагрузки и поведения NimBLE host task. Не вводим очередь без измеренной необходимости.

## 8. Проверки перед фиксацией API

1. Lifecycle NimBLE controller/host для ESP-IDF 6.1 и целевых SoC.
2. Повторный запуск scan и корректная остановка по duration.
3. Адресация и порядок байтов BLE address в публичном API.
4. Поведение при регистрации/снятии драйвера во время активного scan.
5. Поведение при ошибках callback и переполнении внутренних ресурсов.

Решения фиксируются в документации после тестов на устройстве.
